## 2. The approach in one paragraph

Every model and animation is **generated by code**: Blender Python scripts run headless (`blender --background --python script.py`) and export `.glb` files into the Godot project. Godot imports them automatically. An import script in Godot applies our rules on every import: one shared palette material, looping flags, names. The scripts and their parameters are the source of truth, so the whole art set can be rebuilt with one command and restyled by changing data. Characters use **rigid body segments**, each body part a separate low-poly mesh attached to one bone, the way OSRS models move. That needs no weight painting, is easy to animate from code, and lets armour swap piece by piece. All colours come from **one small palette texture** that I can repaint in any 2D editor.

## 3. Art direction

The goal is "reads like OSRS at a glance", not a copy of it.

- **Low-poly and flat-shaded.** No PBR texture sets, normal maps or photo textures. Faces are flat-shaded: set Shade Flat in Blender before export, so normals are split per face.
- **Readability first.** At the default in-game camera distance a player is about 80–120 px tall. At that size you must be able to tell their combat style, gear tier and weapon type, because gear tells the enemy which prayer to use.
- **Chunky proportions.** Slightly large hands, head and weapons, short legs. Weapons are oversized about 1.3× so they read at a distance.
- **Tier = colour + silhouette.** Each gear tier has its own colour (section 7). Higher tiers also gain small silhouette details: trims at tier 4–5, spikes or fins at 6–7. Starmetal and Wyrmforged gear gets a small emissive accent.
- **Team colour** shows on the cape or tabard and in a thin ground ring under each player.
- **Original designs only.** Never copy, trace or import OSRS models, textures, sprites, sounds or game data, and don't model anything to look like a specific OSRS item. Names in the game come from the GDD's in-game names, never the "OSRS analogue" columns.

### Godot import rules

- Blender exports `.glb` straight into `assets/models/...`. Godot imports changed files when the editor regains focus. For scripted builds, run the editor's headless import from the command line; check `--help` on the installed Godot version for the exact flag. Importing doesn't need rendering, so `--headless` is fine for this step.
- Set the project's import defaults for `.glb` scenes so every model uses `tools/import/model_post_import.gd`. That script:
  - Replaces every imported material with `assets/materials/palette.tres`.
  - Checks node names follow the `<slot>__<bone>` rule and the triangle budget, and prints a clear warning if not.
  - Sets loop mode on clips whose names end in `-loop` (idle, walk, run). Godot's glTF importer already honours this suffix; the script makes sure.
- **Palette texture import:** lossless compression, mipmaps off. In `palette.tres` set texture filter to Nearest, roughness 1 and a low specular value. A blurred palette shifts every colour.
- **Manual overrides:** I'm good at Blender. If `art/manual/<asset-id>.blend` exists, the build exports that file instead of the generated one, with the same export settings and naming rules. That way I can hand-fix any model without breaking the pipeline.
- Never edit imported scenes by hand in Godot; changes are lost on re-import. Use the import script, or inherited scenes for gameplay nodes (collision, scripts).

## 6. Character system

### Shared skeleton

Every character uses one armature with these bones. Use underscores, not dots: Godot doesn't allow `.` in node names, so `hand.L` would be renamed and break lookups.

```text
root
└─ hips
   ├─ spine ─ chest ─┬─ neck ─ head
   │                 ├─ upperarm_L ─ forearm_L ─ hand_L ─ socket_offhand
   │                 ├─ upperarm_R ─ forearm_R ─ hand_R ─ socket_weapon
   │                 └─ socket_back            (capes, quivers)
   ├─ thigh_L ─ shin_L ─ foot_L
   └─ thigh_R ─ shin_R ─ foot_R
```

- Blender is Z-up and Godot is Y-up. Let the glTF exporter convert (its default +Y up setting), and never hand-rotate to compensate. A character faces Godot's forward direction (−Z) after import.
- Scale: 1 Blender unit = 1 game tile = the tile size the prototype uses. Check this in A0. A character is about 0.9 tiles tall and stands at the origin.

### Rigid segments

- The body is about 15 separate low-poly meshes (head, chest, pelvis, upper arms, forearms, hands, thighs, shins, feet), each **parented to one bone** in Blender (Parent → Bone). No skin weights.
- On import, Godot turns each bone-parented mesh into a child of a `BoneAttachment3D` that follows its bone. Verify this on the first test character in A2.
- Name each mesh `<slot>__<bone>`, for example `body__forearm_L` or `armour_body__chest`. Code finds the bone from the text after the double underscore.
- Hard joints are fine and on-style. Cap each segment's ends so no gaps show when limbs bend about 90°.

### Gear attachment

| Slot | Bones it uses | Hides body segments |
| --- | --- | --- |
| Helm | head | head (for full helms only; hoods and coifs keep the face) |
| Body | chest, upperarm_L/R, forearm_L/R | chest, upper arms, forearms |
| Legs | hips, thigh_L/R, shin_L/R | pelvis, thighs, shins |
| Boots | foot_L/R | feet |
| Gloves (if added) | hand_L/R | hands |
| Weapon | socket_weapon | — |
| Shield / off-hand | socket_offhand | — |
| Cape / quiver | socket_back | — |

- Each gear item is its own `.glb` containing only its parts, named with the same `<slot>__<bone>` rule. Gear files have no armature.
- Weapon and off-hand origins sit at the grip point, so they snap into the hand sockets with no offsets in code.
- Build a reusable `Character` scene: the imported base body, plus a script that exposes `equip(slot, item_id)` and `unequip(slot)`. Equipping loads the gear scene once (cache it), takes its mesh parts and adds each one under a `BoneAttachment3D` for the named bone. Create the attachment if the bone doesn't have one yet. The script also hides the covered body segments and applies team colour. Each player is just an instance of this scene.

## 7. Palette and colours

- One `palette.png`, 128 × 128, split into 8 × 8-pixel cells: a 16 × 16 grid of swatches. Each gear tier gets a row of a base colour, a darker shade, a lighter highlight, a trim colour and an emissive accent. Fill the remaining rows with skin tones, team colours, wood, stone, foliage, cloth, ice, fire and UI colours.
- Generator scripts never pick colours by value. They ask for a swatch by name from `palette.json` and set every UV of a face to the centre of that cell. One material and one texture for everything means few draw calls.
- Emissive accents: give `palette.tres` an emission texture that's black except in the accent cells. Alternatively, use a second small material for emissive parts only; decide in A1 and tell me.
- Team colour: use per-instance shader parameters (`instance uniform`) or a small material override on team-coloured parts. Don't duplicate materials per player.
- Because colours live only in the PNG, I can restyle the game in a 2D editor. After I edit the PNG, Godot re-imports it and the whole game updates.

## 8. Gear generators

Build gear from **parametric generators**: one Python function per item type, with parameters for size, shape and tier.

- **Melee weapons:** dagger, scimitar (curved blade), longsword, battleaxe, warhammer, plus the unique Whip, Stone Maul, Greatblade, Claws and Void Blade.
- **Ranged weapons:** shortbow, longbow, crossbow, throwing knife, javelin, plus the unique Duskbow, Heavy Ballista and Sunfire Crossbow. Bows take a wood colour per tier. Generate arrows and bolts as projectile meshes too.
- **Magic weapons:** staff (a different head shape per tier), wand, the Forbidden, Eruption and Tempest staffs, and tomes.
- **Armour:** for each style, a helm type (full helm for melee, coif for ranged, hood or hat for magic), body, legs, boots and shield or defender. Sidegrade sets (Berserker, Bulwark, Duelist, and so on) reuse the generators with different parameters and trims.
- **Data coverage.** `data/art/gear_visuals.json` maps every item id in the game's item data to a generator and its parameters. A check script fails if any equippable item has no visual, or if a visual points to an item that doesn't exist.
- **Determinism.** Any randomness uses a fixed seed per asset, so rebuilds give identical files.

## 9. Animations

### Generated from a pose library

- Write poses as data: a pose is a dictionary of bone → rotation (Euler degrees), stored in `art/blender/anims/poses.py`. Build clips by keyframing poses at set times, with the easing given per key.
- Name each Blender action after its clip (for example `attack_slash`, `idle-loop`) and export each action as a separate glTF animation. Exporter option names change between Blender versions, so check them for Blender 5.2 before writing export code.
- Export clips **once**, on the base body. Because every character shares the skeleton, save the imported clips as one shared `AnimationLibrary` resource in `assets/animations/` (set this in the base body's import settings). Every character's `AnimationPlayer` then uses that library.
- Keep animations snappy and stylised, with a little anticipation before each strike. OSRS characters move in clear, readable poses, not motion capture.

### Required clips

| Group | Clips |
| --- | --- |
| Locomotion | `idle-loop`, `walk-loop`, `run-loop` (stance variants per weapon type as needed) |
| General | `eat`, `drink`, `block`, `hit_react`, `death`, `spawn`, `pray_toggle` (small gesture) |
| Melee | `attack_stab`, `attack_slash`, `attack_crush`, `attack_whip`, `attack_2h` |
| Ranged | `shoot_bow`, `shoot_crossbow`, `throw` |
| Magic | `cast_projectile`, `cast_area` |
| Specials | One `spec_<weapon>` clip per weapon with a special attack |

`data/art/anim_sets.json` maps each weapon type to its idle, move and attack clips, so the game picks clips from data.

### Playing them in Godot

- Use an `AnimationTree` on the character: a state machine for locomotion (idle, walk, run), with a OneShot node for attacks, eating, blocking and specials. Cross-fade locomotion over about 0.15 s.
- **Timing (important):** the server decides when an attack happens, on a tick. Start the attack clip on the tick the game reports and line its **impact frame** up with the hit. Store each clip's impact time in `anim_sets.json`; it's simpler and easier to tune than method-call tracks.
- An attack clip must finish within its weapon's attack speed (for example 4 ticks = 2.4 s). Keep attacks around 0.6–1.2 s and let idle fill the rest.
- Scale the walk and run playback speed so a walk cycle covers 1 tile per tick and a run covers 2 tiles per tick.
- **Frozen:** stop locomotion clips and add an ice-shell mesh around the feet (section 10). Attacks still play, because frozen players can attack.

## 10. Effects, icons and visual review

- **Projectiles:** generated arrow, bolt, knife and javelin meshes. Spells are small emissive low-poly shapes plus `GPUParticles3D` (or `CPUParticles3D` on the Compatibility renderer): ember (orange), frost (pale blue), leech (dark red), miasma (green), gloom (purple). Keep particle counts small and pool all effect nodes; don't create and free them every hit.
- **Freeze:** a generated ice-shell mesh at the feet, with a short shatter when the freeze ends.
- **Hitsplats, overhead prayer icons and the special attack bar** are 2D: `Sprite3D` or `Label3D` billboards over players, and `Control` nodes for HUD. I'll paint the final 2D art. Until then, make clean placeholder sprites and list every sprite in `art/2d/sprites.json`.
- **Inventory icons:** a tool scene renders each item's model in a `SubViewport` with a transparent background, from a fixed three-quarter angle. It saves a 64 × 64 PNG with a 1 px dark outline and a soft drop shadow to `assets/icons/`. Icons are always regenerated from models, never drawn by hand.

### Visual review (do this for every phase)

You can't judge art without seeing it, so build this in phase A1 and use it every phase after.

- **Asset viewer:** `tools/dev/asset_viewer.tscn` shows one model, or a full character with chosen gear. It has an animation picker and uses the in-game camera angle, lighting and `WorldEnvironment`.
- **Screenshot mode:** the viewer accepts command-line arguments, for example `<godot> --path . res://tools/dev/asset_viewer.tscn -- --shots <asset-id>`. It sets up each view, waits a couple of frames, saves `get_viewport().get_texture().get_image()` as PNGs into `art/previews/`, then quits.
  - **Godot can't render with `--headless`**, so this runs in a normal window that opens and closes by itself. That's expected on my PC.
- It saves:
  - Each new asset from 4 angles plus the in-game angle.
  - A contact sheet of all 7 tiers of an item side by side.
  - A greyscale version of the contact sheet.
  - A strip of key frames from each new animation.
- Open those PNGs with your Read tool and check them against this list before showing me:
  - [ ] Style, tier and weapon type read clearly at in-game distance
  - [ ] Neighbouring tiers are distinguishable, including in greyscale
  - [ ] No missing faces, flipped normals, z-fighting or gaps at joints
  - [ ] Feet on the ground; weapon in the hand at the grip; shield on the forearm
  - [ ] No limb or weapon passes through the body during animations
  - [ ] Within the triangle budget; colours only from the palette
  - [ ] Matches the rest of the set in scale and style

## 11. Sound effects

- Generate retro-style SFX with jsfxr (a Node package). Check Node is installed first; if it isn't, ask me before installing it. Store each sound as a JSON parameter set in `data/audio/sfx.json` and render it to `assets/sfx/<id>.wav`. Godot imports `.wav` directly; keep it as WAV for short effects.
- Sounds needed: a hit for each style, a miss/block, eat, drink, prayer on and off, special-attack charge, freeze and shatter, each spell element, bow and crossbow release, death, level-up, kill-streak ready, and UI click.
- Keep them short (under 0.6 s, except level-up) and normalise their volumes. Every sound must be distinct, because players react to sound before they see the hit.
- Play world sounds with `AudioStreamPlayer3D` and UI sounds with `AudioStreamPlayer`. Use a small pool of players so many hits in one tick don't cut each other off.
- Music is out of scope for now.
